# Publishing the next pre-release

The public `v0.1.1` tag predates the fix for importing a plugin using the native file picker. Do not overwrite its tag or artifacts. This source prepares `v0.1.2`; preparation is not publication.

1. Merge the fixes into `main` and wait for the required CI checks. Run `node scripts/release.mjs check v0.1.2` and `node --test scripts/release.test.mjs` against the final commit.
2. Create a new `v0.1.2` tag at that commit and create a **draft pre-release** for it. Dispatch the **Release artifacts (Windows + macOS + Linux)** workflow with that tag. It checks out the tag itself, verifies the version, produces the required native packages and CLI binaries, and uploads them with `SHA256SUMS.txt` to the draft.
3. Verify the candidate assets against `SHA256SUMS.txt`. On Windows, macOS and Linux install the actual candidate desktop package in a clean test profile. From the tagged source root, create the same script-free package on each platform with `python -m zipfile -c "Release Picker Smoke Test.mflp" scripts/fixtures/release-picker/manifest.json` (`py -3` can replace `python` on Windows). In Plugins, open the native file picker and cancel first: no plugin should appear. Reopen it, select the `.mflp`, and confirm the approval dialog lists `-Dmfmcl.releasePickerSmoke=true`. Dismiss approval and restart: the plugin must still be inactive and offer review. Approve it explicitly, restart again, and verify it stays active. No game launch or sign-in is required. The mocked browser regression is not a substitute for this native check.
4. Record the tag, exact commit, platform/architecture and per-platform results in the draft notes. Explain that this version fixes local plugin import in the previous pre-release, that package approvals must be granted explicitly, and that the builds are unsigned. Publish the draft only after the native checks pass.

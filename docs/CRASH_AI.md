# 崩溃 AI 分析

用本地 **LFM3-1.7B** 解释 Minecraft 崩溃日志。

- 页面：`http://127.0.0.1:8790/`（独立服务，供设计评审）
- 后端：`crates/crash-ai`（库 + 独立服务 + CLI），同一份代码也接进了桌面版

## 架构演进：从关键词匹配到堆栈因果分析

第一版用关键词规则匹配（「日志里出现 mixin 就报 mixin 失败」）。在**真实崩溃报告**
上这个做法失效了，而且失效的方式很有害：

```text
crash-2026-08-20_13.43.14-client.txt
  java.io.IOException: User limit of inotify instances reached
  	at ...FileWatcher$WatchedDir.<init>
  	at net.minecraftforge.fml.config.ConfigTracker.openConfig
  	at ... {re:mixin}              ← Forge 给每一帧都加这个标记
```

真实原因是**操作系统的 inotify 实例上限**。但堆栈上密密麻麻全是 `{re:mixin}`
（Forge 对每个被改写的帧都这样标注），关键词规则于是报「Mixin 注入失败」——用户
会去挨个关模组，而真正该做的是 `sysctl fs.inotify.max_user_instances=1024`。

现在改为两条互补的通道：

| 通道 | 输入 | 用途 |
| --- | --- | --- |
| `causes.rs` 堆栈因果分析 | 异常链 + 帧 | **决定是什么问题**（权威） |
| `rules.rs` 关键词规则 | 全文 | 在因果分析无结论时兜底；有结论时只保留相关条目 |

关键规则：**因果分析确定类别后，与之无关的关键词规则一律丢弃**。「相关」的判断标准
是「修复动作是否相同」——inotify 上限和 mixin 失败需要完全不同的处理，所以不相关。

因果分析读三样东西，都不是关键词：

1. **异常链**：每个 `Caused by:` 是更深一层，**最内层**才是根因。外层
   `RuntimeException` 包一个 `IOException` 是常态。
2. **抛出的那一帧**：离抛出点最近的、未被插桩的帧属于真正失败的代码。
3. **插桩标记是噪声**：`{re:mixin}`、`pl:mixin:`、`TRANSFORMER/` 表示「这帧被改写过」，
   不表示「这帧失败了」。把它们当作证据正是上面那个 bug 的成因。

## 没有 Java 异常的情况

`hs_err_pid`（JVM 原生崩溃）与看门狗超时都不抛 Java 异常。它们以前会落到「未知」，
而这两类恰恰最难让用户自己看懂：

- **hs_err**：`# A fatal error has been detected` + `Problematic frame` 指向出事的模块。
  如果是显卡驱动（`nvoglv` / `atio` / `opengl32`），结论就是显卡问题。
- **看门狗超时**：`ThreadDeath` + `watchdog`，说明服务器线程被判定卡死。

## Forge 的 `-- MOD xxx --` 块

模组加载失败时，Forge 把真正的原因写在这些块里，而不是异常里：

```text
-- MOD ktice --
	Failure message: Mod ktice requires tconstruct 3.5.2 or above
```

不解析它们，结论就只能停在「模组加载失败」。现在会提取每个模组的 id、缺失的依赖、
要求的版本，并把它们作为证据列出来。真实报告里有 27 条。

## 硬件判断与「彻底带不动」

服务端在每次分析时自动探测本机硬件（`hardware::detect`）：内存、CPU 核心数与主频、
GPU 型号、是否有图形会话、是否软件渲染。

判定是**相对当前整合包**的，不是绝对的：

| 判定 | 含义 | 例子 |
| --- | --- | --- |
| `ample` | 绰绰有余 | 32 GB 跑 20 个模组 |
| `adequate` | 够用 | — |
| `tight` | 吃力但能跑 | 8 GB 跑 300 个模组 |
| `hopeless` | **彻底带不动** | 2 GB 内存 / 单核 CPU / 内存不足所需的一半 |

「彻底带不动」的门槛刻意保守：只有当差距**不可能**通过调设置弥补时才这么判——物理
内存不到需求的一半、单核 CPU、低于 2 GB。措辞也不留余地：这类机器该听到的是「这个
整合包不适合这台电脑」，而不是「试试减少模组」（后者会让用户反复失败）。

两个易错点，都已经有测试钉住：

- **严重度不能靠枚举顺序**。`Verdict` 的 derive 顺序（`Ample < Adequate < Tight <
  Hopeless`）**不是**严重度顺序，早期用 `max()` 取最差项导致「24 GB 内存 + 2 核」
  被判成 `Ample`（因为 `Ample > Tight`），唯一的内存警告被吞掉。现在用显式的
  `severity()`。
- **堆内存超配是设置问题，不是电脑太老**。给 8 GB 的机器分配 8 GB 会被判 `Tight`
  而不是 `Hopeless`——调小一个数字就能解决。

## 模型自身跑不动时的处理

「带不动」在这里指的是**本地模型**跑不动，与游戏能否运行是两件事。两个判断对象
完全不同，混在一起会误导：

| 判断 | 问的问题 | 判据 |
| --- | --- | --- |
| `hardware::assess` | 这台机器能不能跑这个**游戏** | 内存、CPU、是否有图形会话 |
| `feasibility::assess_llm` | 这台机器能不能跑这个**模型** | 内存余量、核数、GPU 加速 |

### 两段式

**1. 静态预估**（分析前）

1.7B / 8k 上下文实测常驻约 1.5 GB（`estimate_llm_memory_mb` 算出 1499 MB，
与本机实测一致）。判断分四档：

| 档位 | 条件 | 行为 |
| --- | --- | --- |
| `viable` | 内存充足 + 多核 + 有 GPU 加速 | 正常使用 |
| `slow` | 能跑，但 CPU 推理或核数偏少 | 提示「每次分析需要十几秒」，仍然使用 |
| `notViable` | 可用内存不到估算值、或不足估算 + 512 MB 余量、或 ≤ 2 核 | **停用模型**，直接给规则结论 |
| `unknown` | 读不到内存（容器/受限环境） | 不武断停用，照常尝试 |

`unknown` 这一档是刻意保留的：探测失败时武断停用，会让一台本来能跑的机器失去功能。
猜错方向的代价不对称——「多试一次」比「错误地关掉」便宜得多。

**2. 运行时熔断**（`LlmHealth`）

静态预估看不了端点填错、模型没加载、内存被别的进程占走。这些只有试过才知道。
连续失败 2 次后自动停用：

- 用 2 次而不是 1 次：一次失败可能是模型正在加载，重试往往就好。
- 停用后**不再等超时**。没有这一层，一台跑不动模型的机器每次点分析都要干等
  90 秒，而规则结论本来几毫秒就能出来。
- 实测：端点不可达时，第 1、2 次约 60–85 ms 失败，第 3 次起直接跳过。

熔断后界面显示的措辞必须与真实原因一致。曾经出现过两条并存的提示——「已跳过模型
分析（按请求）」和「已自动停用（…）」——前者是内部调用传了 `use_model = false`
导致的，读起来自相矛盾，现在会先移除它再写真实原因。

### 界面上的三态

打开页面时 `/api/health` 会同时报告两件事，界面按此显示不同文案：

| 情况 | 状态条 | 附带提示块 |
| --- | --- | --- |
| `notViable` | 这台电脑跑不动本地模型 | 「本地模型已停用（这台电脑跑不动）」+ 内存对比 |
| 已熔断 | 本地模型已自动停用 | 熔断原因 |
| 服务没起 | 模型未连接（仍可只用规则） | 无 |
| `slow` | 模型就绪（CPU 推理，较慢） | 无 |

三种状态的修复方式完全不同：机器不够不该去找模型服务，服务没起不该去换电脑。
所以它们不能合并成一句「模型不可用」。

所有情况下规则分析照常返回，提示块里也明写「规则分析不受影响」。

## 流式输出

模型生成一段完整解释在本机要 6–13 秒。没有流式时，用户面对骨架屏无法区分
「正在推理」和「卡死了」。实测的三段时序现在是：

| 事件 | 时刻 | 内容 |
| --- | --- | --- |
| `rules` | **0.08 s** | 规则 + 因果 + 硬件结论 |
| 第一个 `chunk` | **1.19 s** | 模型开始说话 |
| `done` | 8.29 s | 完整结构（步骤来自规则） |

对照：改之前 `rules` 和第一个 token 都在 **9418 ms** 到达——等于没有流式。

### 踩过的三个坑

**1. 缓冲到最后才写。** 服务端原本把整条 SSE 拼成一个字符串再返回。浏览器在收到
响应头之前不派发任何事件，所以全部内容在最后一起出现。现在路由**先写头**，再逐段
写正文——为此流式路由需要在 `handle` 里直接接管 TCP 流，不能复用
`route() -> Response`（那个签名要求先算完整个 body）。

**2. 快路径掩盖了它。** 修好之前我加了一条「先请求一次只跑规则的接口」的优化，
看起来用户 700 ms 就看到了结论。但直接测 SSE 发现 `rules` 仍在 9418 ms——那条快
路径让界面**看起来**对了，掩盖了流式本身没工作。现在两条路都保留：快路径保证结论
更早出现，流式保证模型文字逐段到达。

**3. 思考块必须实时剥离。** 不能等整个响应结束再剥 `<think>`，否则用户会先看到
推理过程再消失。而增量会把标记切成两半（`</thi` + `nk>`），所以 `ThinkGuard` 是
一个跨块保持的状态机，并保留可能是标记前缀的尾部（`<thi`）不输出。

### 前端

用 `fetch` + 手动读 `response.body`，不用 `EventSource`——后者只能发 GET，而日志有
几 MB，放不进 URL。

模型区域在流式过程中是**稳定的 DOM 节点**，只更新文字，不重画整块：否则每收到一个
字符滚动位置就被打断。闪烁光标是「还在写」的唯一信号，没有它，逐字出现和卡死看起来
一样。`prefers-reduced-motion` 下改为常亮。

## 受控的文件读取

服务支持读取本机崩溃报告，但**只限白名单根目录**：

- `MFMCL_MINECRAFT_DIR` 或 `~/.minecraft`
- 工作目录

判定用 **canonicalize 之后的前缀比较**。`../` 和符号链接都能绕过字面前缀，但绕不过
真实路径。实测 `/etc/passwd`、`~/.ssh/id_rsa`、`../../../etc/passwd` 全部被拒绝。

`/api/sources` 只扫 `versions/*/crash-reports/crash-*.txt`，让用户不必自己找路径。

## 设计原则（评审时请先读这一节）

一个 1.7B 的模型不能独立判断崩溃原因。实测中，它在内存溢出的日志上给出的建议是
**「降低堆内存到 512 MB」**——正好是把崩溃变成必然的方向。所以职责这样切分：

| 做什么 | 谁负责 | 为什么 |
| --- | --- | --- |
| 判断**是什么**问题 | 确定性规则 | 可测试、可回溯，命中就是命中 |
| 解释**为什么**、读这份日志的具体细节 | LFM3 | 这是语言模型真正擅长的事 |
| 给出**怎么做** | 规则（命中时）| 建议是人工整理并测试过的 |
| 规则没命中时的推测与建议 | LFM3，但明确标注 | 没有更好的来源，但要让人知道这是猜的 |

界面上必须始终能看出结论的来源。规则命中和模型推测的视觉、措辞、步骤来源说明
都不一样，这是这套设计的核心，改版时不要把它们合并成一种样式。

## 三种结果的呈现

### 1. 规则命中（最常见）

```
很可能的原因是：内存不足            [很可能] 内存不足   runtime.outofmemory
                                    游戏用尽了分配给它的堆内存……
                                    1. 提高内存分配（按模组数量可加 1–2 GB）
                                    2. 减少模组，或降低视距
                                    ▸ 依据的日志行

[模型解释] 为什么                   lfm3-1.7b
                                    崩溃日志显示在 Arrays.copyOf 时抛出 OutOfMemoryError…
                                    步骤来自匹配到的规则，不是模型生成的。
```

要点：
- 左侧色条按置信度区分（红/橙/灰）
- 规则 id（`runtime.outofmemory`）用等宽小字，供愿意查文档的人
- 模型的步骤一律来自规则，并明写「步骤来自规则」

### 2. 规则未命中，模型推测

虚线框 + 「模型推测」标签 + 「步骤由模型给出，未经规则验证」。这是唯一使用模型
自己建议的场景。

### 3. 模型不可用

顶部横幅说明原因，规则结论照常显示。**不能**把这种情况显示成「分析失败」——
分析是成功的，只是少了一段解释。

## 规则清单

19 条，按失败层分组。每条都有 id、置信度、解释、建议，以及一个 fixture 测试。

| 分组 | 规则 |
| --- | --- |
| JVM 无法启动 | `heap.invalid` `heap.reserve` `jvm.option.invalid` `jvm.option.space` |
| Java 版本不匹配 | `java.class.version` `java.class.version.mismatch` `java.too.new` `java.openj9` |
| 游戏文件 | `files.missing.assets` `files.corrupt.jar` `files.class.notfound` `files.no.main.class` `files.access.denied` |
| 图形 | `gpu.opengl` `gpu.gl.function` `gpu.driver` |
| 模组加载 | `mods.mixin` `mods.duplicate` `mods.missing.dependency` `mods.incompatible` `mods.forge.dependency` |
| 被外部终止 | `runtime.killed` `runtime.headless` |
| 内存 | `runtime.outofmemory` |

### 一个真实的坑

`mods.mixin` 最初只匹配 `mixin` 一个词。每个 Fabric/Forge 的正常启动日志里都有
`SpongePowered MIXIN Subsystem Version=...`，于是**一份完全正常的日志被判成了
Mixin 失败**。现在要求同时出现失败词，并排除子系统横幅。这个 bug 是
`clean-launch` fixture 抓到的——所以 fixture 里必须有一份「什么都没坏」的日志。

## LFM3 的两个坑

**思考模式必须关掉。** LFM3 默认先输出 `<think>` 块。在 CPU 上，1.7B 模型的思考块
会吃掉全部 token 预算，API 返回空的 `content`——看起来像服务坏了。请求里固定带
`chat_template_kwargs: { enable_thinking: false }`，响应里再兜底剥离 `<think>`。

实测对比：思考开 → `''`；思考关 → `'PONG'`。

**置信度用全角冒号。** 模型实际输出 `置信度：高`（全角）。早期只匹配半角，导致
所有分析都静默落到「低」。现在先归一化冒号再匹配。

## 性能实测

本机（CPU，12 线程，Q4_K_M）：

| 场景 | 耗时 |
| --- | --- |
| 规则 only | 4–14 ms |
| 规则 + 模型（典型日志） | 6–13 s |

模型部分慢是必然的：1.7B 在 CPU 上约 26 tok/s。所以界面把规则结果先渲染出来，
模型解释后到再补上——用户不会盯着空白等十几秒。

## 已知限制

- **模型只在 CPU 上跑。** 本机 CUDA 驱动版本与运行时不匹配（`Failed to initialize
  NVML`），llama.cpp 的 CUDA 后端加载失败。CPU 推理可用但慢。换机器或修复驱动后
  把 `-ngl` 调高即可。
- **上下文 8k。** 送进模型的日志片段上限 6000 字符，约 1500 token，留足回答空间。
- **只分析文本。** 不读 JVM 的 hs_err_pid 二进制段，也不读 mods 目录做交叉验证。
- **中文输出固定。** 提示词中文写死，模型只保证简体中文，不做多语切换。

## 接进桌面版

三个命令，与独立服务行为一致：

- `crash_ai_status` —— 模型是否可用
- `crash_ai_analyse` —— 分析日志内容（不读文件）
- `crash_ai_instance_report` —— 取某实例最新的 crash-report

`crash_ai_analyse` 刻意不接收文件路径：日志内容由调用方读好再传。崩溃报告可能来自
实例目录之外（用户从论坛复制的），让后端按路径读取会把「能否读任意路径」变成额外
的攻击面。取实例报告的命令则只在自己管理的 `crash-reports` 目录里找。

## 给评审的具体问题

1. **三种结果样式够不够区分？** 尤其是「模型推测」与「规则命中」在快速扫读时是否
   会被混淆。这是整套设计成立的前提。
2. **规则 id 要不要给用户看？** 现在只有悬停/小字，但它能指向文档。也许该做成可点。
3. **模型解释放在规则下面是否合适？** 另一种排法是模型解释优先（读起来更自然），
   规则作为「已确认的事实」收在下面。
4. **「步骤来自规则」这句说明会不会太技术化？** 它的存在是为了诚实，但普通玩家
   可能不理解「规则」指什么。
5. **缺少日志时的向导。** 现在要求用户自己找到日志文件。是否需要一个「帮我找到
   日志」的入口（桌面版能直接定位实例目录）。

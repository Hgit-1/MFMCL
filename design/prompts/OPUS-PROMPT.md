# 直接交给 Opus 的启动器 UI 设计提示词

使用方法：复制下方分隔线之后的全部内容给 Opus。无需附带现有 UI，也不要附带 PCL/PCL2 截图。若需要 Opus 直接制作可编辑文件，请让它使用具备相应写入或导出能力的设计工具；聊天模型本身不必然具备该能力。

这是独立设计任务的提示词，不要求沿用本项目中任何已生成的界面、名字、配色或布局。

---

你将担任这款产品的产品设计负责人、交互设计师和视觉设计师。请独立构思并制作一套 **Minecraft Java 版桌面启动器的完整 UI/UX 设计**，交付便于我后续修改的设计源文件。

## 一、任务目标

我想从零重建一个成熟的 Minecraft 启动器。它应支持直接发现、下载、自动安装并启动原版或带模组的 Minecraft，同时具备实例管理、内容管理、账户、故障处理与个性化能力。

产品愿景是达到或超越 PCL2 所代表的成熟启动器功能水准，同时让电脑小白无需先学技术知识也能完成主要任务。

本次你的任务是产品体验、视觉界面、组件系统、交互状态和可点击原型，**不是开发真正的启动器后端**。“超越 PCL2”是方向，不是要求你在未核实的情况下宣称已完成全功能对比。以本文具体列出的能力和任务作为设计范围。

## 二、创作自主权与独立性

品牌名称、标志、设计概念、色彩、字体、导航、布局、控件外观、插画及动效语言，都由你独立构思。

- 不参考、复刻或分析 PCL/PCL2 的界面截图、界面源代码、布局、控件造型、品牌与装饰素材；如果工作区存在 PCL 目录，也不要读取或运行它。
- 不把“达到相近功能”理解成“使用相似的信息布局”。从用户任务重新推导结构。
- 不强制绿色、像素字体、方块背景、侧边栏、顶部导航、卡片网格、玻璃拟态或任何既定风格。
- 不必沿用任何现有示例稿。即使我提供了示例，也只把它当作可以被推翻的起点，除非我明确要求保留。
- 可以借鉴成熟桌面软件的一般可用性原则，以及 Material Design、Apple HIG、Fluent 等设计体系的原则，但不要拼贴它们的外观。
- 必要时可以查询官方产品技术文档、平台规则和设计工具文档来确认可行性；不以此为理由搜索 PCL 的视觉参考。不确定的能力标注“待验证”。

请先简洁探索三个真正不同的设计方向，区别应涉及体验与信息组织，而不是只换配色。每个方向说明适用人群、核心思路和代价，总计控制在约 600 字以内。然后自行选择最合适的方向继续制作，除非遇到必须由我决定的阻碍，不要把命名、配色等普通创作决策反复交还给我。

## 三、核心设计原则

### 1. 新手容易上手，熟练用户仍然高效

- 从“我想开始玩”“我想安装整合包”“我想添加模组”等目标出发组织体验，而不是把后端技术模块直接搬进导航。
- 普通安装默认推荐稳定、兼容的选择，自动处理 Java、依赖与合理内存建议。允许高级用户覆盖，但解释风险并可恢复默认。
- 把专业设置渐进展开。第一次使用无需手填 JVM 参数、加载器内部版本号或资源地址。
- “实例”首次出现时，用容易理解的话解释：一套独立的游戏版本、模组、配置和存档。具体展示名由你决定，不强迫新手记住术语。
- 始终清楚显示操作针对哪个游戏、哪个账户；模组安装、存档恢复和删除尤其如此。
- 不以“少点击”为借口省略危险操作确认，也不让普通操作陷入连续弹窗。

### 2. 有设计感，也能日常使用

- 形成统一且有辨识度的视觉语言，避免通用后台模板、满屏等权卡片、装饰过量和只适合宣传截图的布局。
- 重点打磨排版、留白、层级、控件比例、图标一致性、选中反馈、焦点、空状态和状态变化。
- 品牌可以有个性；错误提示、下载进度与启动按钮必须清晰可信。
- 首页不能只有“好看的背景 + 一个启动按钮”，也不能把所有功能平铺。让当前任务、准备状态和下一步有明确关系。

## 四、必须覆盖的功能体验

以下是体验要求，不是强制页面清单。你可以合并、拆分或重组页面，但每项都要有可定位的入口及必要状态，不能只在介绍页写“支持”。

### A. 游戏安装与 Java 管理

- 发现、选择、下载并自动安装 Minecraft Java 原版，区分稳定版、快照和其他测试版本。
- 支持 Forge、NeoForge、Fabric、Quilt 的安装路径；基于游戏版本筛选兼容加载器，不把所有组合都显示为可安装。
- 自动检测及匹配 Java 版本、系统与处理器架构；缺失时提供可信来源和必要许可说明，支持自动安装、手动路径与重新检测。
- 安装前显示清晰的计划：游戏版本、加载器、运行环境、目标目录、预估空间与将执行的操作。未知大小如实标注。
- 处理资源与运行库下载、校验、解压和安装。设计损坏文件、空间不足、权限不足、文件占用、元数据不可用和无兼容版本的恢复路径。
- 明确区分“安装完成”“可以启动”“拥有游戏资格”。

### B. 游戏库、启动与运行

- 游戏配置彼此隔离，避免不同版本的模组、配置与存档混用；共享缓存与游戏私有内容的边界清楚。
- 支持创建、导入、复制、重命名、管理、迁移和移除游戏；删除记录与删除文件不是同一个动作。
- 启动前检查账户、Java、必需资源和基本兼容性；覆盖就绪、检查、修复、启动中、运行中、正常退出、启动失败和异常退出。
- 解释重复启动、启动器留在后台与停止游戏的行为。停止游戏优先引导保存退出，强制结束需说明风险。

### C. 模组、整合包与资源

- 设计 Modrinth、CurseForge 来源下的搜索、筛选、详情、版本选择、安装与更新；包含模组、整合包、资源包、光影和数据包的合理组织方式。
- 展示作者、来源、许可、游戏版本、加载器及适用端；安装到指定游戏之前检查兼容性。
- 安装前展示必需依赖、可选依赖、冲突、重复项及未知兼容情况。允许用户理解本次会增加、替换或停用哪些内容。
- 支持整合包导入与导出，至少覆盖 `.mrpack` 和 CurseForge 清单式整合包；未知 ZIP 不能直接当成已支持的整合包。
- 资源受平台或作者限制时，明确进入手动补齐流程：说明原因、跳转官方项目页、提示所需文件、选择本地文件、校验后继续。不绕过分发限制。
- 导出默认排除凭据与私人数据；存档等需明确选择；受限资源按许可用清单、链接或排除说明表达。
- 更新前预览影响并提供可行备份与恢复，不承诺自动解决所有模组冲突。

### D. 账户、皮肤与离线使用

- 使用微软官方授权流程，经系统浏览器登录；不在启动器内收集微软密码、不仿制官方登录页。
- 覆盖等待、取消、超时、拒绝授权、回调失败、授权过期、重新授权与账户切换。
- 区分登录成功、Java 版所有权已确认、所有权未知和未拥有。没有所有权时不能用离线入口绕过。
- 离线只适用于符合授权条件、已合法获取且本地完整的内容；不能承诺离线下载缺失资源或连接需要在线认证的服务器。
- 设计账户移除与凭据处理说明；皮肤与披风按真实权限展示，区分本地预览、提交中、失败与服务确认生效。

### E. 下载、取消和故障恢复

- 用一致的任务体验展示排队、解析、下载、校验、解压、安装、待手动处理、暂停、失败、取消请求、取消完成及成功。
- 总量未知时使用不确定进度；暂停与断点续传仅在底层支持时出现。
- 断网、限流与应用重开后，让用户知道哪些成果保留、哪些需要重新执行、下一步是什么。
- 区分暂停、取消安装、关闭窗口和结束游戏。某阶段只能等到安全点取消时，明确显示正在等待，不假装立即完成。
- 新安装提交前、更新提交后、导入已有文件冲突分别处理。仅在存在备份或事务记录时承诺恢复；说明不能自动恢复的外部变化。
- 保护用户原有文件与其他游戏；不要用一句“失败后自动回滚”跳过实际边界。

### F. 存档、备份与诊断

- 存档管理、手动与自动备份、范围选择、空间提示、备份历史、恢复预览和覆盖确认。
- 恢复前保留当前状态；运行中的游戏不进行不安全覆盖。备份失败、恢复失败和部分恢复需要独立反馈。
- 崩溃排查区分日志证据、可能原因与建议操作，覆盖 Java 不匹配、内存不足、依赖/模组问题及未知原因，不把推测写成确诊。
- 日志导出或分享前提供预览与脱敏，上传需用户明确同意，不能展示或分享访问令牌。

### G. 个性化、设置与服务器

- 浅色、深色、跟随系统；可探索主题、背景、透明度、字体缩放与动效设置，提供实时预览和恢复默认。
- 自定义背景不能破坏阅读、焦点和错误提示；提供遮罩、可读性保护与安全回退，尊重减少动态效果偏好。
- 服务器收藏、添加、编辑、刷新、版本和连接信息；区分在线、未知、不可达与信息过期，不能把添加成功当成成功入服。
- 不默认假设具备免费联机穿透、自动开服或其他未接入服务；如果提出扩展，标注提供方、前提、权限、费用及待接入状态。

## 五、文件与可编辑性要求

### 优先成果

优先交付 Figma Design 原生设计文档，并在工具支持时导出真实 `.fig`。如果你的实际工具更适合其他格式，也接受真实可编辑的 `.sketch`、`.xd`、Pixso 原生工程，或目标导入工具认可的 Axure ZIP 工程包。**选择一种能可靠交付的格式即可，不要求同时生成所有格式。**

开始大量制作前，请先确认当前工具是否真的具备创建、编辑和导出目标文档的能力。必要时先做一个包含可编辑文字与控件的小样验证；不可仅凭能输出 JSON、代码或图片，就认定能交付目标文件。

如果无法生成这些原生格式，请简短说明具体能力限制以及需要我提供的工具或连接。可以先继续做设计构思与规格，但明确标注原生文件尚未交付，不要用伪造文件替代。

### 原生设计文档标准

- 页面、区块、文字、图标与控件合理分层并命名，文字可编辑；不要用整页截图或一张大 SVG 代替原生界面。
- Figma 使用 Frame、Auto Layout、组件实例、变体、组件属性、样式及适用的 Variables；其他工具使用其等价原生能力，并说明不能等价保留的部分。
- 建立语义色彩、排版、间距、圆角、控件尺寸和反馈规范；浅深色不是只替换背景。
- 常用控件具备适用的默认、悬停、按下、焦点、禁用、加载和结果状态；变体有真实用途，不为数量堆重复组件。
- 可点击原型包含主流程、关键失败分支、返回与取消，主要操作有有效目标。
- 外部授权、文件选择、下载和游戏运行在原型中明确为模拟，不发起真实登录或系统文件修改。
- Figma Make 网页、React/HTML 代码、截图、PDF、SVG、说明文档可以补充，但不等于可编辑设计源文件。普通 ZIP 也不自动等于 Axure 工程。禁止靠修改扩展名冒充目标格式。

## 六、窗口适配与可访问性

以桌面应用为主，Windows 优先，同时考虑 macOS、Linux 的窗口控件和交互差异，不需要制作手机端来凑页面数量。

- 主要流程至少覆盖 1440×900 与 1024×720 两档窗口。采用真实重排、伸缩、滚动和信息收敛，不能只把整页缩小。
- 浅深色均验证主要任务；中文长名称、英文文件名、路径、长版本号、125% 与 150% 字体缩放应有处理规则。
- 普通文字对比度至少 4.5:1，大文字至少 3:1；关键边界与焦点清楚，状态不能只用颜色区分。
- 明确键盘操作、焦点顺序、弹窗焦点约束、退出后焦点返回以及减少动态效果规则。原型工具无法验证的真实屏幕阅读器行为标注待开发测试。

## 七、执行顺序与范围控制

1. 简短确认工具和可交付格式，列出必要假设。
2. 提出三个方向并自主选型；给出信息架构和核心用户流程。
3. 先完成最关键的纵向流程：首次使用 → 推荐原版安装 → Java 自动匹配 → 安装过程 → 授权与启动 → 运行/失败反馈。保留一条清楚的原版路径，不要把原版选择误接到强制安装加载器的流程。
4. 将核心视觉和组件系统应用到模组、整合包、游戏管理、账户、备份、个性化、下载与诊断；补齐对应失败与取消状态。
5. 制作两档窗口和浅深色的关键适配，连接原型，完成走查。
6. 整理真实源文件、原型入口、使用说明及尚未完成或未验证的事项。

如果单次上下文或工具额度不足，按上述顺序分批制作并维护清楚的待办。不要把完整任务悄悄缩减为一张首页，也不要在只完成构思时宣布全部交付。无需为了符合某个页面数量而拆出无意义的画板。

## 八、交付前必须走查的任务

至少检查以下任务，并简短记录结果与真实位置；设计原型通过不代表真实后端已实现：

1. 新手不手填 Java 参数，完成推荐原版安装并到达首次启动结果。
2. 创建带加载器的游戏，安装有依赖的模组，处理一次不兼容版本；Forge、NeoForge、Fabric、Quilt 都有合理的选择或不支持反馈。
3. 安装整合包，遇到受限文件，经官方页面引导、错误文件校验、正确文件补齐后继续。
4. 下载中断网、恢复、校验失败重试；取消下载与提交阶段取消的最终状态各自正确。
5. 微软授权取消或超时后重试；无所有权、资格未知和离线条件不会被混同为可启动。
6. 安装、启动、返回管理全过程指向同一个目标游戏；账户与游戏名称不会无解释地变化。
7. 运行中恢复存档被安全阻止；退出后先保护当前存档，再恢复指定备份。
8. 崩溃后能理解可能原因，并预览脱敏日志后决定是否分享。
9. 改变主题或背景、缩小窗口、放大字体后，主要操作与错误信息仍然可读可达。
10. 修改一个共享组件、一个主题色和一个长标题，确认相关界面能够正确跟随或重排，证明设计稿适合继续编辑。
